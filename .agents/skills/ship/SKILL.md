# Landing work on main

## Applies to

The ask is to get changes onto `main`: a bare "push", "ship it", "land
this", "merge this". A bare "push" is the phrase most likely to be read
as license to push straight to `main`. This skill exists so it isn't.

Other git asks mean less:

| ask | what to do |
|---|---|
| "push this branch" | `git push` it. No PR, no gates. |
| "open a PR" (no merge ask) | Open it and stop. Steps 3 and 4 are not yours to run. |
| "commit this" | Commit. Pushing was not asked for. |
| any other branch named outright | Push directly there. |
| fork, non-`origin` remote | An ordinary push. |

If you're unsure whether an ask means landing on `main`, ask. Assuming
*no* is the mistake this skill prevents.

## 1. Fetch, then is it green?

```sh
git fetch origin
git status -sb
git log --oneline origin/main..HEAD
scripts/check
```

`scripts/check` is exactly what CI runs, so a red one here is a red PR.
For a branch with several commits, check that **each** commit is green
on its own, each in a throwaway detached worktree (skill
`use-a-worktree`):

```sh
for c in $(git rev-list --reverse origin/main..HEAD); do
  git worktree add -q --detach /tmp/wt-check "$c"
  /tmp/wt-check/scripts/check >/dev/null 2>&1 && echo "ok   $c" || echo "FAIL $c"
  git worktree remove --force /tmp/wt-check
done
```

## 2. Branch, commit, open the PR

Never commit onto `main`. If you have commits on a local `main`, move
them: `git branch <branch>`, then read `git status --short` (anything that
isn't yours, stop and ask), then point `main` back at `origin/main` and
check out `<branch>`.

- Branch name and first commit line carry a type prefix: `feat/`,
  `fix/`, `docs/` for the branch; `feat:`, `fix:`, `docs:` for the
  commit.
- Commit named paths, not whatever happens to be staged:
  `git commit -- <paths>`. The body says what changed, why, and what was
  verified, and describes only what this commit contains.
- The trailer is `Co-Authored-By: <agent>`, name only (AGENTS.md,
  Conventions).

Write the PR body to a file under `.github/pull_request_template.md`'s
headings, with the `🤖 Generated by an LLM agent` line at the top and the
bottom. A generated-by footer the harness injects, whatever its wording,
counts as the bottom one. A body in
a file, not inline, keeps backticks from being executed by the shell.

```sh
git push -u origin <branch>
gh pr create --base main --body-file <body-file> --title "<type>: <summary>"
```

For a change to a check, the body says what is now enforced and how that
was verified (AGENTS.md, "Public text").

## 3. Gate, then ask

```sh
gh pr checks <n> --watch
gh pr view <n> --json state,isDraft,mergeStateStatus,baseRefName,headRefOid,commits
```

READY means: open, not a draft, base `main`, and `mergeStateStatus` is
`CLEAN`. `mergeable` alone only means "no conflicts", so don't gate on
it. Not ready: fix what's red (`gh run view <run> --log-failed`), push,
and gate again. Don't ask.

Ready: show the title, URL, commit list and the merge method, then ask
**one** question that covers both merging and deleting the branch. Use
rebase for a single commit, and a merge commit for several, whose messages
carry reasoning a squash would flatten.

**On no:** leave the PR open, say so, stop.

## 4. Merge, then delete, on yes only

```sh
gh pr merge <n> --rebase --match-head-commit <headRefOid>   # or --merge
gh pr view <n> --json state          # must read MERGED
git push origin --delete <branch>    # if GitHub didn't already
git branch -D <branch>
```

`--match-head-commit` pins the merge to the commit you gated and showed
the user, so a push in between can't slip in. A failed merge deletes
nothing; report it and don't retry silently. Report the merge commit and
what happened to the branch.

## Stacked PRs

A PR based on another PR's branch is retargeted to `main` before its
base merges (`gh pr edit <child> --base main`), so it never depends on
what GitHub does to it when the base branch is deleted. Each PR still
gets its own merge-and-delete question, and the body says which PR it
is stacked on.
